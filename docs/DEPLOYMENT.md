# Strata RMM — Deployment Reference

**Last updated:** 2026-08-20

This document identifies deployment paths that are actually backed by the current repository. It does not treat the presence of a Helm chart, KOTS files, development Compose files, or cross-compiled binaries as production acceptance evidence.

For step-by-step installation, use [INSTALL.md](INSTALL.md). For upgrades use [UPGRADE.md](UPGRADE.md); for rollback/recovery use [ROLLBACK.md](ROLLBACK.md).

## Supported self-hosted deployment paths

| Deployment | Current source-backed status | Authoritative entrypoint |
|---|---|---|
| Docker Compose on 64-bit Linux | Primary self-hosted pre-beta path | `scripts/install-platform.sh --mode docker` |
| Native Linux package | Supported with operator-supplied TLS PostgreSQL/NATS and HTTPS boundary | `scripts/install-platform.sh --mode native` |
| Kubernetes / Helm | Configuration exists, but built-in install/update/rollback acceptance is not yet proven | Not an accepted automatic lifecycle |
| Windows orchestrator service | Not a supported orchestrator deployment path | None |
| macOS orchestrator | Not a supported orchestrator deployment path | None |

Endpoint-agent platform support is separate from orchestrator deployment support. Do not infer server support from an agent build target.

## Docker Compose production installation

The authoritative production Compose bundle is `deploy/docker/docker-compose.install.yml`. Do not start it by inventing environment values or by building the orchestrator locally as a promoted release.

From a verified release checkout:

```bash
sudo ./scripts/install-platform.sh \
  --mode docker \
  --domain rmm.example.com \
  --admin-email owner@example.com
```

The secure installer owns production preflight, secrets, TLS material, PostgreSQL/NATS configuration, schema migration, initial administrator bootstrap, HTTPS readiness, and the protected Compose environment. See [INSTALL.md](INSTALL.md) for the complete contract.

The production orchestrator image is an immutable `repository@sha256:<digest>` reference. Mutable tags such as `latest` are not a deployment authority. The normal orchestrator service does not receive the host Docker socket.

To validate configuration without starting services:

```bash
sudo env STRATA_BOOTSTRAP_PASSWORD_FILE=/protected/admin-password \
  ./scripts/install-platform.sh \
  --mode docker \
  --domain rmm.example.com \
  --admin-email owner@example.com \
  --prepare-only
```

Preparation creates protected installation material; follow the cleanup/replay guidance in `INSTALL.md` before retrying.

### Docker operations

Use the protected environment generated by the installer:

```bash
docker compose \
  --env-file deploy/docker/.install.env \
  -f deploy/docker/docker-compose.install.yml ps
```

Do not substitute the development Compose topology for the production bundle.

Verified Docker upgrades use the root-only host wrapper:

```bash
sudo ./scripts/update-docker-platform.sh
```

That wrapper mounts Docker-socket access only into a transient updater utility and applies only a signed-manifest immutable OCI candidate. See [UPGRADE.md](UPGRADE.md).

## Native Linux package deployment

Native deployment requires a locally verified versioned `.deb` or `.rpm` release package plus existing secure dependencies. A representative invocation is:

```bash
sudo ./scripts/install-platform.sh \
  --mode native \
  --domain rmm.example.com \
  --admin-email owner@example.com \
  --package-file ./strata-rmm-orchestrator_VERSION_ARCH.deb \
  --database-dsn-file /secure/postgres-dsn \
  --nats-url tls://broker.example.com:4222 \
  --nats-advertise-url tls://broker.example.com:4222 \
  --nats-token-file /secure/nats-token \
  --nats-ca-file /secure/nats-ca.crt
```

The native installer copies protected dependency inputs, creates generated application secrets, installs the version-matched UI and orchestrator package, performs bootstrap, and enables `strata-rmm.service`.

The default native HTTPS mode is external. When an installed trusted Caddy package is dedicated to this deployment, automatic HTTPS may be requested as documented in `INSTALL.md`. The installer does not fetch and execute a mutable reverse-proxy bootstrap script.

Operational checks use the real service name:

```bash
systemctl status strata-rmm.service
journalctl -u strata-rmm.service --since "15 minutes ago"
```

## Development Compose topology

`deploy/docker/docker-compose.yml` is a development topology, not production install guidance. It may use development-oriented connectivity/credentials supplied by the developer and must not be exposed as a supported internet-facing deployment.

Start development resources only through repository development instructions and never copy development secrets, plaintext transports, or mutable-image examples into production configuration.

## Kubernetes / Helm boundary

The repository contains Helm/Kubernetes resources for engineering and future deployment work. Their existence does not establish the same pre-beta lifecycle guarantees as the Docker/native paths.

Until a separate acceptance gate proves immutable release selection, secret/TLS setup, database compatibility, controlled upgrade, rollback, readiness, and representative-host evidence, do not describe Kubernetes as a supported automatic Strata RMM installation or upgrade path. Generic `helm install`, `helm upgrade`, or `helm rollback` commands are therefore intentionally not published here as production procedures.

## Release provenance

Promoted deployments must originate from the repository's signed versioned release process. The release manifest binds:

- semantic release version;
- exact source SHA;
- minimum supported upgrade version;
- schema compatibility;
- immutable OCI image/digest where applicable;
- versioned native artifacts and checksums;
- Sigstore identity tied to the protected release workflow/tag.

A local source checkout, branch build, mutable container tag, or manually copied executable is not equivalent to a promoted release.

## Network and TLS boundary

Production deployments require encrypted authenticated dependency paths as defined by [INSTALL.md](INSTALL.md) and [CONFIGURATION.md](CONFIGURATION.md). In particular:

- browser/API traffic must terminate at HTTPS;
- production NATS requires TLS and authentication;
- production PostgreSQL must use TLS/SCRAM according to the installation model;
- application/runtime secrets must come from protected files/secrets rather than examples embedded in documentation;
- public NATS exposure is limited to the agent messaging endpoint required by the installed topology.

## Acceptance evidence

Source configuration and CI prove deterministic repository contracts; they do not prove a specific host. Before claiming internal-alpha/beta readiness, retain representative-host install, upgrade, rollback, restart, data-preservation, and cleanup evidence in [HOSTED_INTERNAL_ALPHA_EVIDENCE.md](HOSTED_INTERNAL_ALPHA_EVIDENCE.md) and the applicable Phase 8 gate records.
